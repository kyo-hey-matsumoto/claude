# Webサイト改修提案一式（01〜08）

## 概要

Webサイト/ECサイトの改修・リニューアル提案を、番号を振った8種類のドキュメントセットとして作成する型。DR.WU（drwu.jp）案件（`clients/drwu/website-renewal-2026/`）で確立し、実際に運用した構成。各ドキュメントのID（FR-/F-/SCR-/WBS番号/T-）を一貫させることで、要件→機能→画面→WBS→テストの対応関係を後から誰でも追えるようにする。

## 8点セットの構成

| No. | ファイル | 中身 | 前提 |
|---|---|---|---|
| 01 | `01-project-overview.md` | 背景・目的・ゴール・スコープ（対象/対象外）・体制やスケジュールの前提 | なし |
| 02 | `02-requirements.md` | 課題→FR-01, FR-02...の機能要件、非機能要件の位置づけ（詳細は06に逃がす）、対象外事項 | 01 |
| 03 | `03-directory-map.csv` + `03-screen-list.csv` | ディレクトリマップ（第1階層〜urlなど、既存サイトの棚卸し＋改修後の姿）／画面一覧（URL単位ではなくテンプレート単位でSCR-01, SCR-02...） | 02 |
| 04 | `04-feature-list.csv` | F-01, F-02...。Shopify標準／アプリ／独自開発などプラットフォームの実装区分、優先度(Must/Should/Could) | 02, 03 |
| 05 | `05-wireframes/` | 主要画面のみのHTMLワイヤーフレーム（全画面は原則やらない。03の画面一覧に「ワイヤーフレーム対象」列を持たせて絞る） | 03, 04 |
| 06 | `06-external-integrations.md` | 外部連携一覧（連携先/目的/対応要件/データ方向/認証/コスト）、データ設計概要、非機能要件一覧 | 04 |
| 07 | `07-wbs.csv` | WBS。担当領域・人日・相対週(Week1〜)で構成し、開始時期に依存させない | 04, 05, 06 |
| 08 | `08-test-items.csv` | テスト項目T-01, T-02...。対象機能(F-ID)と紐づける | 04, 06 |

## 進め方

1. **まず要件を確定させる**（開発体制、リリース時期の目安、ワイヤーフレームの対象範囲など）。ここが曖昧なまま04〜08まで作ると手戻りが大きい。AskUserQuestionで3点前後に絞って先に決める
2. 02の機能要件FR-IDを確定してから03〜08に展開する。IDは変えず、後続ドキュメントすべてで同じ番号を使い回す
3. 03は「ディレクトリマップ」と「画面一覧」を分ける。ディレクトリマップはURL/ナビ構造の資料、画面一覧はテンプレート単位（同じデザインを使い回すURL群を1画面としてまとめる）の資料。両者は目的が違うので混ぜない
4. 05は全画面を作らない。03の画面一覧に優先度・対象フラグを持たせ、主要5〜8画面だけに絞る
5. 07のWBSは「人日」を基本単位にする。体制（内製/外部ベンダー）が未定な段階では金額を出さない。リリース時期が未定なら絶対日付ではなく相対週(Week1, Week2...)で書く

## クライアント提出用スプレッドシート化

03・04・06（あるいは指定された番号）を1つのxlsxに複数タブでまとめ、クライアント提出用の体裁を整える依頼が来ることがある。`build_client_spreadsheet.py` をベースに、Python + `openpyxl` でタブごとにCSV/MD由来のデータを流し込み、以下のトーン&マナーで整形する。

- ヘッダー行: 濃いグレー背景 + 白文字太字、フリーズ
- 区分の色分け（既存/新設/レガシー、Shopify標準/アプリ/独自開発など）は淡いパステル系のみ。原色は使わない
- 優先度(Must/Should/Could)は色ではなく文字の濃淡（太字・グレー階調）で表現する
- 各シート冒頭にタイトル行＋説明行を入れる（何のシートか、対象範囲、注意書き）

このトーン&マナーは `web-design/CLAUDE.md` の標準として固定済み。案件ごとの配色指定がない限りこれをデフォルトにする。

## 重要な制約: Google Drive MCPへの直接アップロードには文字数上限がある

`mcp__claude_ai_Google_Drive__create_file` にxlsx等をbase64で直接アップロードしようとすると、ペイロードが長い場合に `The file content is not a valid base64 string` で失敗することがある（実測: 4,000文字は成功、29,500文字は失敗。閾値は不明だが数千〜数万文字の間にある）。base64文字列そのものは正しくても失敗するため、リトライしても直らない。

**対応**: ファイルは `clients/<client>/<project>/` 配下に保存してgit管理する。Google Sheets化が必要な場合は、ユーザー自身にGoogleドライブへドラッグ&ドロップ（または「新規>ファイルのアップロード」）してもらう案内に切り替える。ドライブ側は自動でGoogle Sheets形式に変換してくれるため数秒で完了する。

大きいbase64を送る前に、まず数千文字程度のダミーデータで疎通確認すると、この制約に早く気づける。

## 参考実装

`clients/drwu/website-renewal-2026/` に01〜08一式＋`05-wireframes/`＋クライアント提出用xlsxの実例がある。新しい案件で流用する際は、このディレクトリ構成をコピーして中身を差し替えるのが最短。
